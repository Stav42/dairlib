Why the Current C3 Fine-Manipulation Controller Underperforms

A code-level analysis of the C3 plan, the Allegro execution path, the IK projection, contact-force semantics, the cube-release transient, and the controller architecture required to make C3 materially responsible for object manipulation.

Analysis only — no implementation Evidence: /tmp/c3_ik_sine_roll_dz.log 20 August 2026

1. Executive conclusion

The current experiment is not a faithful execution of a C3 plan. It transforms C3’s predicted state, discards C3’s optimized control input, and reinterprets C3’s contact reaction as an independently commandable actuator. Consequently, even a mathematically excellent C3 solution is not expected to reproduce its predicted cube motion.

The failure is architectural rather than a single bad cost weight. Three problems are stacked on top of one another:

  1. Planner/executor mismatch: C3 optimizes joint torque u, but the OSC path ignores it.
  2. Lossy state transformation: the already full-order C3 joint state is converted through FK and a loose, redundant IK solve.
  3. Incorrect contact-force execution: lambda is rescaled incorrectly and collapsed to a normal-only force.
Interpretation The latest high state weights have made the raw first C3 knot locally reasonable. The current log therefore does not show that C3 is incapable of fine manipulation. It shows that the rest of the program does not execute the optimization problem C3 solved.

2. What the latest log proves

0.05–0.07 rad Typical raw first-knot joint displacement
0.02–0.03 rad Typical displacement after IK projection
1.0–1.7 mm Frequently accepted Cartesian projection residual

2.1 The catastrophic joint-plan explosions are largely gone

The earlier multi-radian and out-of-range q[1] plans are absent in this run. Every displayed projection succeeds, the raw displacement remains local, and no NaN or fallback is reported. Higher state penalties therefore helped regularize the optimizer.

2.2 The projection substantially changes what C3 requested

A common sample changes from approximately raw_dq = 0.065 to projected_dq = 0.027. In joint norm, the projection is removing roughly 55–65% of the planned displacement. Some of that difference can be redundant posture, but it also changes joint Jacobians, velocities, future contact geometry, and the dynamics that made the C3 prediction valid.

2.3 “Projection OK” is a narrow numerical statement

It means that IK placed the fingertip points within a tolerance of positions obtained by forward-kinematics of C3’s q1. It does not establish that:

  • the fingertips lie on the actual cube surface;
  • the predicted cube pose and fingertip pose remain mutually consistent;
  • the same contact mode, normal, or witness point is preserved;
  • the C3 velocity or force trajectory is realizable;
  • the nonlinear SAP plant will follow the linearized C3 prediction.

2.4 The implemented controller is overwhelmingly position-driven

In the settled portion of the displayed log, |tau_pd| is commonly near 1 N·m while the implemented |tau_lambda| is around 0.05–0.075 N·m. Torque norms do not directly equal object-level authority, but they clearly show that the current behavior is dominated by kinematic PD rather than by the C3 contact term.

3. The displayed jerk is primarily a cube-unpin transient

thandoff = 3.373 s   +   0.500 s pin hold   =   3.873 s release

The jerk reports begin at t = 3.87 s, exactly when the hard kinematic pin is removed. The commanded roll is still printed as zero. This timing is too exact to treat as a coincidence.

What the pin does physically During the 0.5-second warm-up, the fingers push into the cube while the code overwrites the cube pose and velocity after every simulation step. The cube cannot move to its loaded equilibrium. When that overwrite stops, accumulated contact preload and penetration unload into the free cube as an acceleration spike.

The report label [JERK] is itself slightly misleading: the implementation takes one finite difference of cube velocity, so it detects acceleration, not the derivative of acceleration. The early events therefore do not demonstrate that the sine trajectory has a discontinuous mathematical jerk.

Experimental correction Initialize the unpinned hand–cube system close to a force-balanced equilibrium, or release the constraint continuously. Exclude the immediate release window when evaluating fine-manipulation tracking. This release transient is separate from the earlier ring-to-C3 contact-set handoff problem.

4. The central error: C3’s control contract is broken

C3 solves a local complementarity dynamics problem of the form:

xk+1 = A xk + B uk + D λk + d
Variable Meaning in the Allegro C3 model What the OSC executor currently does
x 16 hand positions, cube pose, 16 hand velocities, cube twist Takes only q1, transforms it through FK→IK, then position-tracks it
u The 16 commandable Allegro joint torques Discarded in --exec_mode=osc
λ Contact-force coefficients jointly constrained by complementarity Reinterpreted as an independent, normal-only force command
C3 optimizer Predicts x, joint torque u, and contact reaction λ together
→
Lossy reinterpretation q1→FK→IK; u0 dropped; λ collapsed and rescaled
→
Different closed-loop system gravity + pure position PD + ad hoc Jᵀ normal force

The predicted cube trajectory is only consistent with the particular u and λ appearing in the C3 solution. Once u0 is replaced by a different PD law, the prediction no longer describes the executed system.

Why the zero-lambda ablation made C3 appear irrelevant In OSC mode, removing the lambda-derived term leaves only the PD controller because the actual C3 input u0 was already absent. That experiment revealed the execution mismatch; it did not establish that C3’s optimized control input had no value.

5. Lambda is not being executed with correct semantics

5.1 Lambda is endogenous, not a second actuator

Lambda is selected jointly with state and input so that the contact complementarity model closes. In the full-hand model, the commandable input is joint torque u. Lambda is the contact reaction predicted to emerge under that motion and torque. It cannot be independently imposed while simultaneously replacing u with an unrelated PD law.

5.2 The frictional direction is discarded

The Anitescu model constructs cone directions approximately as:

Jc = EtTJn + μJt

Each lambda coefficient therefore acts along a combined normal–tangential friction-cone direction. The Allegro executor sums the coefficients into one scalar and applies a hard-coded cube-face normal. Fine rolling depends precisely on tangential traction, so this discards the most important portion of the planned wrench. It also uses the fingertip frame origin rather than the actual contact witness point, changing the moment arm.

5.3 The physical lambda is divided by its scale a second time

C3::Solve() converts the stored force solution back to physical units before returning. The API states:

λphysical = GetLambdaScaling() · λinternal

Nevertheless, the executor computes GetForceSolution()[0] / GetLambdaScaling(). That converts the already physical value back toward the internal scaled coordinate. The adjacent source comment claiming the division recovers physical units is incorrect.

5.4 Relinearization can change applied force without a new plan

UpdateLCS() may update the current scaling. If relinearization runs every 5 ms while C3 solves every 40 ms, the stored force plan comes from the old solve but the executor divides it using the newly updated scale. The applied term may consequently jump on a relinearization tick despite there being no new C3 solution. A reported event with solve_age=21 ms and relin_age=1 ms is consistent with this mechanism.

6. Why the C3→FK→IK projection is not the right abstraction

The Franka reference needs a task-space-to-full-order mapping because its C3 model is reduced. The Allegro C3 model is already full order: q1 contains all 16 Allegro joint positions. Projecting it through fingertip FK and then IK is therefore not model reduction; it is a lossy remapping of an existing full-order prediction.

6.1 The accepted error is exactly explained by the IK box

IK permits ±1 mm independently in each Cartesian coordinate. Therefore an accepted point may be as far as √3 mm ≈ 1.732 mm from its nominal target. The observed maximum of 1.70659 mm is the expected edge of that feasible box, not evidence of high-precision contact.

6.2 The solve is under-specified

The projection contains position constraints and an initial guess, but no explicit posture continuity objective, fingertip orientation target, surface-normal condition, contact-frame constraint, or desired velocity. Redundant IK can therefore move to a different joint-space branch while remaining nominally position-feasible.

6.3 It does not certify contact consistency

The projection targets are generated from hand FK alone. They are not recomputed from the C3-predicted cube pose at knot 1, and they are not constrained to the cube’s signed-distance surface. Preserving three world points approximately does not preserve the contact model that gave C3 its predicted object motion.

6.4 It changes the timing

C3’s first future knot is 50 ms ahead, while the ramp reaches that knot over a typical 40 ms solve period. The executor therefore asks for the planned state about 20% faster than the model that generated it, and restarts the interpolation whenever a new solve arrives.

Correct response to invalid C3 joint states If q1 violates joint or velocity limits, those constraints belong inside C3. Post-processing an invalid trajectory into a different one destroys the dynamic consistency that is the principal reason to use MPC.

7.1 The contact model is especially weak for roll

Rolling changes the cube-face normals and moves each fingertip witness point. A single linearization repeated across a 250 ms horizon assumes those quantities stay local. Without a trust region, C3 is allowed to request a motion for which its own matrices are no longer a faithful approximation.

7.2 The friction parameters are not identical

The simulation cube uses static friction 0.8 and dynamic friction 0.5, while the LCS is commonly run with --mu=0.5. The LCS therefore lacks the simulator’s larger static sticking region. Near stick–slip transitions, this changes the contact mode and force needed to initiate motion.

7.3 High state weights solve the symptom but suppress C3’s role

Large hand-state penalties prevent grotesque joint predictions, which is useful. But the desired hand state itself comes from IK. As the weight grows, C3 increasingly becomes an expensive tracker of a manipulation trajectory selected outside C3. The dynamically meaningful portion—the optimized torque u—is then ignored by OSC.

8. What the Franka reference actually does

The reference implementation uses a reduced C3 plant whose controlled end effector has three translational degrees of freedom. C3’s u is consequently a real three-dimensional end-effector force, not a hidden 7-joint torque vector and not lambda.

Reduced C3 EE state + object state; commandable EE force u
→
Timestamped references EE position trajectory + exact u trajectory
→
High-rate OSC Force tracking, position tracking, acceleration limits, smoothing

The Franka pipeline publishes GetInputSolution() as end_effector_force_target. Its low-level OSC then realizes the state and the exact commandable input together. It does not publish or directly execute C3’s lambda trajectory.

Why the analogy matters The Allegro c3_ik path claims to mirror the reduced-model/full-order-tracker separation, but its C3 model is not reduced. Converting a 16-joint C3 state back through IK does not reproduce the reference architecture.

9. Recommended solution

Choose one coherent planner/controller contract. Two valid designs exist; the present hybrid should not be tuned further as though it were one of them.

Near-term validation path

Full-order joint-space C3

Keep the current full Allegro state, but faithfully execute the input it optimizes.

  • Add hard q, v, u, and Δu bounds.
  • Add joint/fingertip trust regions and acceleration limits.
  • Relinearize and solve atomically on the same cadence.
  • Use τ = suu0 + K(x*−x).
  • Use q* and v* as feedback references, not a pure PD command.
  • Keep lambda diagnostic-only during the first validation stage.
  • Remove the FK→IK projection.
Recommended final architecture

Reduced task-space multi-finger C3

Make C3 choose object/contact behavior in coordinates the hand controller can realize.

  • State: cube pose/twist and fingertip/contact-frame positions/velocities.
  • Optionally include surface coordinates, gaps, or low-dimensional grasp synergies.
  • Input u: commandable full 3D fingertip forces or contact-frame commands.
  • High-rate whole-hand QP/OSC maps state and exact u to joint torque.
  • QP enforces joint, velocity, acceleration, torque, rate, and posture constraints.
  • Lambda remains the internal predicted contact reaction/contact-mode variable.

9.1 Coherent full-order feedback law

τ(t) = suu0C3 + K(t)(x*(t) − x(t))

The feedforward term is the command C3 used in its prediction. The feedback term rejects modeling error around the nominal plan. A constrained inverse-dynamics QP or local TVLQR is preferable to pure position PD because it can track position and velocity while enforcing actuation and acceleration limits.

9.2 Better contact-aware MPC

For larger motion, use time-varying linearizations along a nominal trajectory, successive convexification, or contact-implicit MPC with explicit trust regions. At minimum, shorten the horizon until predicted witness-point and normal motion remains genuinely local.

9.3 Make plan and model an atomic bundle

A control plan must retain the exact LCS, input scale, lambda scale, contact basis, and witness points under which it was solved. Do not update one of those objects independently while the executor continues consuming an older plan.

10. Research-grade validation protocol

Before committing to either architecture, separate optimizer quality, model quality, and execution quality with a one-step nonlinear rollout test.

  1. Capture one complete C3 solution.
    Store the common initial state x0, optimized u0, physical lambda0, predicted x1, contact basis, and scaling values.
  2. Check the optimization residuals.
    Report ADMM consensus, complementarity, dynamics equality, input bounds, and trust-region violations. “Solver returned a solution” is not a convergence certificate.
  3. Run a nonlinear one-step experiment.
    Starting from the identical, unpinned x0, apply the exact C3 u0 to the 1 ms SAP plant for one 50 ms C3 interval.
  4. Compare prediction with reality.
    Measure cube pose/twist, fingertip positions, signed gaps, contact mode, witness points, full contact wrenches, and x1_SAP − x1_C3.
  5. Add feedback and repeat.
    Compare exact u0, feedback-only, and u0 + feedback. Keep direct lambda injection disabled so the causal role of C3 input remains identifiable.
  6. Only then evaluate long-horizon fine manipulation.
    Once one-step predictions are credible, evaluate roll/dz tracking after the release transient and quantify RMS/peak object error rather than relying only on visual inspection.
Decision rule If the SAP one-step rollout matches C3 under exact u0, the planner is useful and the primary fault is execution. If it does not, improve the linearization, contact model, and trust region before building a more elaborate tracker around that prediction.

11. What will not solve the root problem

  • Increasing k_hold indefinitely: makes the state plan tame but increasingly turns C3 into an IK tracker.
  • Increasing the velocity weight alone: slows the plan without repairing the planner/executor contract.
  • More ADMM iterations alone: may improve convergence but cannot make a different low-level controller execute the C3 dynamics.
  • Tightening only the IK tolerance: reduces one source of Cartesian error but still transforms and retimes the plan.
  • Crossfading lambda: hides an abrupt command but preserves the wrong force semantics and scaling.
  • Multiplying lambda by zero: is a useful ablation, but in the current OSC path it also removes nearly the only remaining C3-derived actuation.
  • Judging the first 100 ms after unpin: mostly measures release preload, not fine-manipulation quality.
C3 should be judged only after its exact commandable input and predicted state are realized together by a controller whose constraints and timing match the model interface.
