The OSC Executor — --exec_mode=osc

A joint-space inverse-dynamics + task-space contact-force controller that realizes the C3 plan on the exact nonlinear plant, instead of replaying whatever the plan's linearized model assumed. This document explains the problem it solves, exactly where every number comes from in the code, the math behind each term, and how it compares to the two executors that came before it.

1. The problem this solves

C3 (Consensus Complementarity Control) is a receding-horizon MPC that, every solve, returns three mutually-consistent trajectories over a short horizon: states x, inputs u, and contact forces λ. They are "consistent" only inside the model it solved — the Linearized Complementarity System (LCS), a linear-plus-complementarity approximation of the real contact dynamics, re-derived fresh at every relinearization. "Applying the plan" means taking that first step and turning it into a torque command on the real, non-linear, full-friction-cone Drake simulation. How you do that last step is a separate design decision from the planner itself, and it turned out to matter enormously.

1a. Two executors were tried before this one

ModeWhat it appliesWhat happened
--exec_mode=direct
Architecture A		 τ = s_u·u₀ — literally play back the plan's own first input, nothing else. FAILED The fingers went limp and fell, as if no torque was applied at all. This showed that u₀ alone cannot be trusted as a complete, directly-appliable torque command — whatever gravity/dynamics compensation the LCS's linearization assumed, it was not enough to hold the real hand up.
--exec_mode=task_space
legacy hybrid, default		 Hand-tuned PD-to-q_contact while pinned; after release, a Jacobian-transpose grip force plus task-space PD to a fixed fingertip target plus s_u·u₀ as a small feedforward. WORKED, BUT FOR THE WRONG REASON It held the cube, but nearly all of the holding force came from the hand-tuned PD and grip-force terms, not from the plan. It doesn't actually test whether C3's plan is good — a stiff-enough PD controller would hold almost any reasonable grasp on its own.

Neither answers the real question: if you faithfully realize what C3 planned — its intended hand configuration and its intended grip force — on the true dynamics, does the grasp hold? That's what --exec_mode=osc is built to answer.

Why not just add gravity comp back to direct mode? Because that only patches one specific failure (gravity) using the same untrustworthy source (the LCS's own model) and says nothing about whether the rest of the input — the part meant to realize the grip and any Coriolis/inertial coupling — is correct either. The principled fix is to stop trusting the LCS for actuation entirely and use the real plant.

2. The design: two feedforward terms, computed on the real plant

C3 hands the executor exactly two physically meaningful things per solve: a target configuration one step ahead, and a target contact-force allocation for right now. The OSC executor takes only those two — nothing else from the LCS — and realizes them with exact rigid-body dynamics.

\[ \tau_{\text{hand}} \;=\; \underbrace{\tau_{\text{motion}}}_{\substack{\text{joint-space}\\\text{inverse dynamics}}} \;+\; \underbrace{\tau_{\text{force}}}_{\substack{\text{task-space}\\\text{contact force}}} \]

2a. Term 1 — joint-space motion (computed-torque control)

Goal: drive the hand toward the configuration the plan says it should be at one step from now.

Where the target comes from:

const std::vector<VectorXd> xplan_now = c3->GetStateSolution();
q_des  = xplan_now[1].head(n_hand_q);            // planned hand joint angles, one step ahead
qd_des = xplan_now[1].segment(n_pos, n_hand_v);  // planned hand joint velocities, one step ahead

allegro_grasp_c3_squeeze.cc:1774–1779

GetStateSolution() returns the plan's state trajectory x₀…x_N over the horizon; index [1] is the state one c3_dt after now — i.e. where the plan intends the system to be next, not where it is right now ([0]). The state layout (documented at the top of the file, lines 786–789, and reused here) is 

positions  [0 .. n_hand_q-1]        : hand joints        (16)
positions  [n_hand_q .. n_pos-1]    : cube quaternion+xyz (7)
velocities [n_pos .. n_pos+n_hand_v-1] : hand joint vel   (16)
velocities [n_pos+n_hand_v .. n_x-1]   : cube vel         (6)

which is exactly why q_des is .head(n_hand_q) and qd_des is .segment(n_pos, n_hand_v).

The control law is standard computed-torque / inverse-dynamics control. First form a desired joint acceleration from a PD law on the tracking error:

\[ \ddot q_{\text{cmd}} = k_p\,(q_{\text{des}} - q) \;+\; k_d\,(\dot q_{\text{des}} - \dot q) \] 
const VectorXd qddot_cmd_hand =
    FLAGS_osc_kp * (q_des - q_hand) + FLAGS_osc_kd * (qd_des - v_hand);

allegro_grasp_c3_squeeze.cc:1781–1782  ·  gains: --osc_kp (default 300), --osc_kd (default 15), defined at lines 242–247

Then convert that acceleration into the exact torque that would produce it on the real plant, using the full rigid-body equations of motion

\[ M(q)\,\ddot q + C(q,\dot q)\,\dot q = \tau_g(q) + \tau_{\text{applied}} \quad\Longrightarrow\quad \tau_{\text{applied}} = M(q)\,\ddot q_{\text{cmd}} + C(q,\dot q)\,\dot q - \tau_g(q) \]

Drake computes the right-hand side directly — mass matrix, Coriolis/centrifugal terms, and gravity, all evaluated at the plant's actual current state, not the plan's linearization point — via MultibodyPlant::CalcInverseDynamics: 

VectorXd vdot_full = VectorXd::Zero(sim_plant.num_velocities());
sim_plant.SetVelocitiesInArray(sim_allegro, qddot_cmd_hand, &vdot_full);
drake::multibody::MultibodyForces<double> applied_forces(sim_plant);
sim_plant.CalcForceElementsContribution(plant_ctx, &applied_forces);  // gravity!
const VectorXd tau_id =
    sim_plant.CalcInverseDynamics(plant_ctx, vdot_full, applied_forces);
const VectorXd tau_motion =
    sim_plant.GetVelocitiesFromArray(sim_allegro, tau_id);

allegro_grasp_c3_squeeze.cc:1784–1790

Why vdot_full is built for the whole plant, not just the hand. sim_plant also contains the free-floating cube, so CalcInverseDynamics needs an acceleration value for every one of the plant's velocity coordinates, not just the hand's 16. The cube's slots are left at zero. This is safe: the hand and the cube are separate kinematic trees with no joint between them, so the mass matrix is block-diagonal between them and the Coriolis terms don't cross between trees either — whatever the cube's chosen vdot entries are, the returned hand rows of the generalized force are unaffected. GetVelocitiesFromArray/SetVelocitiesInArray extract and inject exactly the hand's block of a full-plant vector by model instance, so no manual index bookkeeping is needed.
Gravity is NOT automatic — you must supply it. Drake's CalcInverseDynamics(context, vdot, external_forces) computes τ = M(q)v̇ + C(q,v)v − τapp, where τapp comes only from whatever is in external_forces. It does not add gravity by itself. So CalcForceElementsContribution (which loads gravity, joint damping, etc. into applied_forces) must be called first; then the returned torque is M v̇ + C v − τgravity — computed torque with gravity compensation. Passing an empty MultibodyForces omits gravity entirely, so at a static hold (v̇≈0, v≈0) the returned torque is ≈0 and the finger joints droop as if unactuated. (This was a real bug in an earlier version of this executor: the fingers fell in Meshcat despite the plan looking fine.)

2b. Term 2 — task-space contact force (the "operational space" piece)

Goal: exert the grip force the plan says is needed at each fingertip, right now, along the direction that presses into the cube.

Where the force target comes from:

const std::vector<VectorXd> lam_plan_now = c3->GetForceSolution();
const VectorXd lam0 = lam_plan_now[0] / c3->GetLambdaScaling();

allegro_grasp_c3_squeeze.cc:1794–1795

GetForceSolution() returns the plan's contact-force trajectory λ₀…λN-1; index [0] is the force the plan says should be active right now (paired with input u₀, which this executor otherwise ignores). It comes back in the solver's internal scaled units, so it is divided by GetLambdaScaling() (the AnDn_ factor) to recover physical Newtons — the same scaling rule documented in c3.h and already used throughout the diagnostic prints in this file.

Each contact's normal-force component is picked out of the flat 30-entry λ = [γ(3) | λn(3) | β(24)] vector via normal_groups[i], the same per-contact index groups the rest of the file already uses for the same purpose: 

for (int i = 0; i < 3; ++i) {
  double fn = 0.0;
  for (int idx : normal_groups[i]) fn += lam0(idx);
  ...
}

allegro_grasp_c3_squeeze.cc:1802–1804

Mapping a Cartesian force to joint torque is the classic operational-space step: the Jacobian-transpose relation

\[ \tau_{\text{force}} \;=\; \sum_{i=1}^{3} J_i(q)^\top \, \big(f_n^i\, \hat n_i\big) \]

where Ji is fingertip i's translational Jacobian (world frame, hand-columns only) and n̂i is the direction that presses into the cube face for that finger, rotated into the world by the cube's current orientation: 

Eigen::MatrixXd J(3, sim_plant.num_velocities());
sim_plant.CalcJacobianTranslationalVelocity(
    plant_ctx, drake::multibody::JacobianWrtVariable::kV,
    sim_plant.get_body(tip_bodies[i]).body_frame(), Vector3d::Zero(),
    sim_plant.world_frame(), sim_plant.world_frame(), &J);
tau_force += J.leftCols(n_hand_v).transpose() * (fn * (R_WC * press_C[i]));

allegro_grasp_c3_squeeze.cc:1805–1811  ·  press_C = {(0,1,0), (0,1,0), (0,-1,0)}, the same fixed per-finger press direction (in the cube's local frame) already used by the task_space executor, rotated by R_WC from the cube's live pose (CubePoseFromPositions).

Summed over the three fingers, this is the second term added into the final command:

tau_hand = tau_motion + tau_force;

2c. After both terms: the shared safety clamp

Like every other C3-phase executor in the file, the combined torque is clamped to the physical torque budget before being sent to the simulator — this is the same guard that stopped an unclamped 321 N·m spike at pin-release from wrecking the grasp in an earlier debugging session: 

if (phase == kC3) {
  tau_hand = tau_hand.cwiseMin(FLAGS_tau_max).cwiseMax(-FLAGS_tau_max);
}

3. What this executor deliberately does not use

  • C3's input solution u₀ — not read at all in this mode. The whole point is to stop trusting the LCS's own actuation channel and instead realize the plan's motion and force intentions directly on the true dynamics.
  • Hand-tuned task-space PD to a fixed fingertip target (as in task_space mode) — the motion target here comes from the plan's own next state, not a fixed geometric grasp point, so a good plan is required for this executor to track something sensible.
  • Force floors (--force_floor in task_space mode) — the commanded normal force is exactly what C3 planned, with no artificial minimum propping it up. If the plan under-grips, this executor will under-grip too, by design: that's what makes it a real test of the plan.

4. Why this is the right test of the planner

Because this executor does not add any independent stabilizing controller of its own beyond exact physics realization of what C3 already decided, its success or failure is attributable to the plan itself, not to the executor compensating for the plan's weaknesses. Concretely:

  • If the grasp holds under osc mode, C3's planned configuration and grip force are genuinely sufficient to hold the cube on the real dynamics — the plan is validated end-to-end.
  • If it still fails, the failure is in the plan (its target configuration or its force allocation), not in how faithfully that plan was realized — ruling out actuation-mapping bugs as the culprit and pointing back at the C3 cost/solver/model tuning already investigated (--w_cube_vel, --rho_scale, --admm_iter, --w_G).

5. Running it

bazel run //examples/sampling_c3:allegro_grasp_c3_squeeze -- --lcm_publish=true \
  --k_hold=0 --w_vel=0 --mu=0.5 --num_friction_directions=4 \
  --rho_scale=1.08 --admm_iter=100 --w_G=0.5 --w_cube_vel=100 \
  --exec_mode=osc --osc_kp=300 --osc_kd=15

--osc_kp/--osc_kd are untuned defaults. Overshoot or ringing → lower osc_kp. Sluggish tracking of the plan's motion → raise it. Because CalcInverseDynamics already accounts for the true mass matrix, these gains behave like a proper acceleration-space PD (units: rad/s² per rad and per rad/s), not a raw torque-space PD — they should not need to be anywhere near the task_space executor's --task_kp/--task_kd or the pinned-phase --kp/--kd.

A caveat worth stating plainly. This inline implementation is a hand-built, minimal version of operational-space control — a joint-space computed-torque term plus a task-space Jacobian-transpose force term, summed. It does not use an operational-space (task) inertia matrix \(\Lambda = (J M^{-1} J^\top)^{-1}\) to properly decouple the two objectives, and it does not resolve any conflict between the motion and force terms via a QP. dairlib has a full OSC framework (systems/controllers/osc/: operational_space_control.h, inverse_dynamics_qp.h, joint_space_tracking_data.h, external_force_tracking_data.h, and friends) that does this properly, with friction-cone and torque-limit constraints inside the QP. Migrating to it would be the natural next step for a production-quality controller, but requires restructuring this file's manual simulation loop into a Drake system diagram — a bigger change deliberately deferred here in favor of a fast, in-loop answer to "does the plan actually hold."
