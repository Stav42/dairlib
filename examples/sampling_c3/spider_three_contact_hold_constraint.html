C3 / spiderwalk diagnostic note

Removed three-finger C3 state-box constraint

A record of the hard state constraint that was tried, then removed from C3.

August 30, 2026  •  Candidate fingers: middle + thumb + ring

Short answer

This was a hard constraint inside the C3 optimization problem. It has now been removed. C3 no longer constrains its predicted cube state to this box.

It used to say: at every future state predicted by C3, the cube must remain close to its stationary target pose and must move slowly. That requirement was later-added and has been removed from the C3 problem.

The former C3 constraint

Let the cube part of C3's predicted state at knot \(k\) be:

\[ Sx_k = \begin{bmatrix} q_k \\ p_k \\ \omega_k \\ v_k \end{bmatrix}. \]
  • \(q\): the four-number cube orientation quaternion.
  • \(p\): cube world position \([x\;y\;z]\).
  • \(\omega\): cube angular velocity.
  • \(v\): cube linear velocity.

The reference is the first target state in the C3 horizon, horizon_target_[0]. During this candidate-support phase it is the stationary cube target at the requested small yaw.

                 C3 prediction horizon

 current state        knot 1             knot 2             ...       final knot
     x(now)  ─────►    x1   ─────►    x2   ─────►           xN
                        must be inside       must be inside                  must be inside
                       ┌─────────────┐     ┌─────────────┐              ┌─────────────┐
                       │ target box  │     │ target box  │              │ target box  │
                       └─────────────┘     └─────────────┘              └─────────────┘

The constraint is applied to every C3-predicted state knot, not just the last one.

Exact hard inequality

For every predicted state knot, C3 previously received the following componentwise box constraint:

\[ \begin{aligned} \ell &\le Sx_k \le u, \\[0.6em] q^\ast - \sin(0.10/2)\,\mathbf{1}_{4} &\le q_k \le q^\ast + \sin(0.10/2)\,\mathbf{1}_{4}, \\ p^\ast - 0.005\,\mathbf{1}_{3} &\le p_k \le p^\ast + 0.005\,\mathbf{1}_{3}, \\ \omega^\ast - 0.25\,\mathbf{1}_{3} &\le \omega_k \le \omega^\ast + 0.25\,\mathbf{1}_{3}, \\ v^\ast - 0.05\,\mathbf{1}_{3} &\le v_k \le v^\ast + 0.05\,\mathbf{1}_{3}. \end{aligned} \]

Here \(q^\ast, p^\ast, \omega^\ast, v^\ast\) come from the stationary target state. Thus \(\omega^\ast\) and \(v^\ast\) are zero for this hold.

Why it could cause an infeasible solve

For the middle–thumb–ring candidate, C3 must satisfy all of these at the same time:

C3 must find:     torque sequence u0...N-1 and contact-force sequence λ0...N-1

such that:           predicted dynamics are obeyed
                     contact forces obey normal/contact/friction rules
                     each active finger keeps its 0.05 N normal-force margin
                     torques stay within their limits
                     [removed] every predicted cube state stays inside the box above

If no such u and λ exist:  C3::Solve final QP failed with InfeasibleConstraints

This constraint was intentionally added as a safety test, but it is now removed. C3 may now solve a candidate that drifts; the existing after-solve viability check will reject it before index is allowed to lift.

How a corrective yaw would use C3 and OSC

A corrective yaw is a new, short cube-reference trajectory. It is not a hand-tuned finger-force command and it is not an extra yaw torque injected outside C3.

1. Put the current state and yaw reference into C3

While index, middle, and thumb are still touching, C3 receives:

  • the measured hand and cube state, including cube pose and velocity;
  • the current three-contact contact/friction linearization;
  • the C3 horizon of desired cube poses, whose yaw is a smooth path toward the requested \(10^\circ\) yaw; and
  • the normal contact, friction, and torque constraints.

For the original turn, the yaw component of the reference is a smooth path from zero to the goal:

\[ \psi_{\mathrm{ref}}(t): 0 \longrightarrow \psi_{\mathrm{goal}} = 0.1745\ \mathrm{rad}. \]

With --track_cube_contact=true, this cube reference also produces an IK posture reference for the fingertips.

2. C3 solves its ordinary short-horizon plan

At each scheduled C3 solve, it computes a new horizon of planned states, contact forces, and inputs:

\[ \{x_k,\lambda_k,u_k\}_{k=0}^{N-1}. \]

C3 is free to choose the force allocation needed to follow the yaw reference while satisfying its constraints. There is no prescribed middle/thumb/index force split.

3. OSC turns the C3 result into actuator torque

In --exec_mode=osc, the direct C3 input \(u_0\) is not sent straight to the motors. OSC instead uses the first planned C3 contact force \(\lambda_0\) as its contact-force objective and combines it with the IK joint posture target:

\[ \tau_{\mathrm{actuated}} = \tau_{\mathrm{OSC\ force}}(\lambda_0) + \tau_{\mathrm{posture\ PD}}(q_{\mathrm{IK}},q,\dot q). \]

For these tests the posture term uses osc_kp=0.5 and osc_kd=0.0. The resulting hand torque is what reaches the simulator, which then produces the actual cube motion.

4. Measure the yaw error

The cube yaw is measured from its actual pose, not inferred from the planned force. The residual is:

\[ e_\psi = \operatorname{wrap}\!\left( \psi_{\mathrm{goal}} - \psi_{\mathrm{measured}}\right). \]

For the latest run before ring placement, the cube was near \(0.299\ \mathrm{rad}\) while the goal was \(0.1745\ \mathrm{rad}\), so the needed correction was about \(-0.124\ \mathrm{rad}\), or \(-7.1^\circ\).

5. If necessary, start a second smooth yaw segment

This is the proposed feedback phase; it is not implemented yet. If \(\lvert e_\psi\rvert\) exceeds the yaw threshold, the gait keeps the same three contacts and does not place ring. It creates a new short reference that starts at the measured yaw and ends at the original goal:

\[ \psi_{\mathrm{corr}}(\tau) = \psi_{\mathrm{measured}} + s(\tau)\left( \psi_{\mathrm{goal}}-\psi_{\mathrm{measured}} \right), \qquad 0\le s(\tau)\le1. \]

Here \(s(\tau)\) is a smooth ramp. At the start of this correction, the reference equals the measured yaw, so the command does not jump.

6. Re-solve C3; do not rebuild the contact model

The new yaw-reference horizon is put into C3, and C3 solves fresh ordinary plans at its normal solve cadence. The contact set remains {index, middle, thumb}, so there is no C3 topology rebuild and no three-contact candidate test yet. Rebuilding is reserved for a contact-set change, such as ring joining or index leaving.

The solve/OSC/measure loop repeats until yaw, position, and velocity meet the settling gate. Only then does the gait place ring, later evaluate the middle–thumb–ring C3 hold, and potentially move index.

Current behavior is open-loop at the maneuver level: it commands one nominal \(0\!\to\!10^\circ\) yaw reference and proceeds by time. It does continue to solve C3, but it does not create this deliberate measured-yaw-to-goal correction segment before ring placement.

Why normal-only execution does not fully close the C3 feedback loop

Rejecting C3's noisy joint-input plan is reasonable. The problem is not that C3's input \(u\) is ignored; the problem is that the current OSC branch also discards the tangential part of C3's contact-force plan.

What C3 plans

For the Stewart--Trinkle contact model, C3's first force vector has the layout:

\[ \lambda_0 = \begin{bmatrix} \gamma \\ \lambda_n \\ \beta \end{bmatrix}. \]
PartMeaningPhysical force to execute?
\(\gamma\)Friction-cone slack variables.No. They are not physical contact forces.
\(\lambda_n\)Normal contact compression at each fingertip.Yes.
\(\beta\)Tangential/friction force rays at each fingertip.Yes.

What the current OSC branch executes

It extracts only one normal-force scalar per active finger:

\[ f_{n,i} = \sum \lambda_{n,i}, \qquad \tau_{\mathrm{OSC\ force}} = \sum_{i\in\mathrm{active}} J_i(q)^\mathsf{T}\bigl(f_{n,i}n_i\bigr). \]

It drops \(\beta\) entirely. Thus the current execution branch is a normal-force proxy, not an execution of the full C3 contact-force plan.

A normal scalar for each finger does not uniquely specify the six-dimensional wrench on the cube. It may hold the cube, but it cannot in general reproduce C3's planned net force and yaw torque.

Why this matters for automatic MPC correction

C3 does re-solve from the measured cube state. If the cube yaw is wrong, it can plan a corrective contact wrench. But that planned correction often needs tangential/friction force and its moment arm about the cube centre:

\[ M_z^{\mathrm{C3}} = \sum_i \left[ (p_i-p_{\mathrm{cube}}) \times f_{i,\mathrm{cube}}^{\mathrm{C3}} \right]_z. \]

Normal-only OSC can create some yaw torque through geometry, but it is not guaranteed to create \(M_z^{\mathrm{C3}}\). The coupled planner/executor loop can therefore settle at the wrong yaw even though C3 keeps observing and re-solving from that yaw.

The appropriate force-only execution bridge

Keep C3's joint input \(u\) out of the actuator loop. Instead, reconstruct the complete physical force that C3 planned on the cube at each active contact:

\[ f_{i,\mathrm{cube}}^{\mathrm{C3}} = \lambda_{n,i}b_{n,i} + \sum_j \beta_{i,j}b_{\beta,i,j}. \]

The existing C3 linearization already stores the exact world-frame bases \(b_{n,i}\) and \(b_{\beta,i,j}\). Use those bases; do not invent a second tangent basis in OSC.

Then command the equal-and-opposite desired force at the fingertip using the measured hand Jacobian:

\[ \tau_{\mathrm{force}} = \sum_i J_i(q_{\mathrm{measured}})^\mathsf{T} f_{i,\mathrm{hand}}^{\mathrm{desired}}, \qquad f_{i,\mathrm{hand}}^{\mathrm{desired}} = -f_{i,\mathrm{cube}}^{\mathrm{C3}}, \]

with the final sign chosen consistently with the simulator's Jacobian and contact-force convention. The total safe actuator command is then:

\[ \tau = \tau_{\mathrm{gravity}} + \tau_{\mathrm{force}} + \tau_{\mathrm{posture}}. \]

The posture term remains only a low-gain stabilizer. For these tests it retains osc_kp=0.5 and osc_kd=0.0; it does not need C3's predicted joint state or joint input.

Recommended diagnostic before adding a special yaw correction phase

Log both the planned and the simulator-resolved contact wrench:

\[ \begin{aligned} M_z^{\mathrm{C3}} &= \sum_i [(p_i-p_{\mathrm{cube}})\times f_{i,\mathrm{cube}}^{\mathrm{C3}}]_z, \\ M_z^{\mathrm{SAP}} &= \sum_i [(p_i-p_{\mathrm{cube}})\times f_{i,\mathrm{cube}}^{\mathrm{SAP}}]_z. \end{aligned} \]
  • If C3 plans a corrective \(M_z\), but SAP does not produce it, the force executor is losing the C3 plan.
  • If C3 itself plans nearly zero corrective \(M_z\), then the C3 cost, model, or constraints need investigation.
This produces a deliberately force-level controller: measured state \(\rightarrow\) C3 force plan \(\rightarrow\) full contact-force executor \(\rightarrow\) cube \(\rightarrow\) measured state. It avoids applying the unreliable C3 joint-input sequence while preserving the feedback content of the contact plan.

Measured-wrench outer loop for force-only yaw control

The force-only C3 executor needs one more feedback layer: compare the actual wrench on the cube with the wrench required to reduce the measured pose error, then make a bounded contact-force correction. C3 remains the nominal force planner; this outer loop does not apply C3's noisy joint input \(u\).

Why it is needed

In the 30 degree four-contact experiment, at \(t=5.4\) s, C3 and the reconstructed OSC command both requested \(+0.005692\) N m of world-\(+Z\) moment, while SAP resolved essentially zero:

\[ M_z^{\mathrm{C3}} = M_z^{\mathrm{OSC}} = +0.005692\ \mathrm{N\,m}, \qquad M_z^{\mathrm{SAP}} \simeq 0. \]

The cube consequently stopped near \(0.240\) rad (about 14 degrees) despite a \(0.524\) rad (30 degree) yaw reference. The resolved normal forces also differed sharply from the C3 normal commands. This is an execution/contact mismatch: a planned wrench is not yet evidence that the cube receives that wrench.

1. Form a desired object wrench from measured error

At an outer-loop rate such as 20--50 Hz, measure cube pose and twist. For yaw, form a bounded PI-D correction around C3's nominal yaw moment:

\[ e_\psi = \operatorname{wrap}(\psi_{\mathrm{ref}}-\psi),\qquad M_{z,\mathrm{des}} = M_{z,\mathrm{C3}} + K_\psi e_\psi + K_{\dot\psi}(\dot\psi_{\mathrm{ref}}-\dot\psi) + K_I\!\int e_\psi\,dt. \]

Clamp this command and use anti-windup. In the actual implementation the same idea should produce a complete six-dimensional desired wrench: yaw correction plus limited roll/pitch and position corrections. Pure yaw control is unsafe when the cube is already rolling or pitching.

2. Estimate the wrench SAP actually applies

Use the resolved simulator contact points and forces, not the C3 witness forces:

\[ \hat w_{\mathrm{SAP}} = \sum_i \begin{bmatrix} f_i^{\mathrm{SAP}} \\ (p_i-p_C)\times f_i^{\mathrm{SAP}} \end{bmatrix}. \]

On hardware, replace SAP with a contact-wrench observer or force/torque sensing. The yaw feedback error is then \(M_{z,\mathrm{des}}-\hat M_z^{\mathrm{SAP}}\), not \(M_{z,\mathrm{des}}-M_z^{\mathrm{C3}}\).

3. Reallocate only the missing wrench

Build the grasp map \(G_{\mathrm{actual}}\) from the measured cube pose and current contact positions. Solve a small constrained QP for a force correction around C3's first-knot force plan:

\[ \Delta\lambda = \arg\min_{\Delta\lambda} \left\|G_{\mathrm{actual}}\Delta\lambda- \left(w_{\mathrm{des}}-\hat w_{\mathrm{SAP}}\right)\right\|_Q^2 + \rho\|\Delta\lambda\|^2, \qquad \lambda_{\mathrm{cmd}} = \lambda_{\mathrm{C3}}+\Delta\lambda. \]

Constraints must retain positive normal compression, friction-cone margin, actuator limits, and a small per-update force-rate limit. The regularization term prevents the controller from needlessly changing the internal squeeze forces that already hold the cube.

4. Execute and close the loop on the cube, not on planned forces

Reconstruct the full normal-plus-tangential force from \(\lambda_{\mathrm{cmd}}\), convert it to fingertip torque through the measured Jacobians, and repeat the measurement. The resulting loop is:

\[ \text{cube pose/twist} \longrightarrow w_{\mathrm{des}} \longrightarrow \text{constrained force allocation} \longrightarrow J^\mathsf{T}f \longrightarrow \text{cube} \longrightarrow \hat w_{\mathrm{SAP}}. \]

5. Include an authority test; do not integrate forever

This outer loop is not magic. Before allowing its integral term to grow, apply small, safe force-allocation perturbations and estimate the local execution effectiveness:

\[ B_{\mathrm{eff}} \approx \frac{\Delta w_{\mathrm{SAP}}}{\Delta\lambda_{\mathrm{cmd}}}. \]

If every feasible perturbation produces negligible \(\Delta M_z^{\mathrm{SAP}}\), the present contact geometry and force-only execution have no usable yaw authority. Freeze the yaw integrator, retain the holding wrench, and report the failure. The remedy is then a different contact layout or a carefully controlled hand-motion component—not arbitrarily larger force commands.

The first implementation is now available behind --osc_wrench_feedback=true. It is deliberately a yaw-only outer loop: bounded PI yaw-moment correction, measured-SAP contact geometry, tangential force redistribution, per-contact force/rate limits, and an authority timeout. It requires --exec_mode=osc --osc_full_contact_force=true. Roll, pitch, and translational wrench feedback remain future work.
