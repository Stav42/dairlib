1. Experiment Design & Objective

The physical question underneath this file is simple: can a linearized contact-implicit optimizer (C3) hold a cube against gravity using only friction from a 3-finger squeeze, and can it be made to do so through real actuation rather than "on paper"? Two nested experiments sit inside the one binary:

1a. The physics experiment — does the grip survive?

Three Allegro fingertips (index, middle, thumb) squeeze a 6 cm, 0.2 kg cube along its ∓Y faces. Only friction — not the normal force itself — can support the cube's weight, since the squeeze is lateral and gravity is vertical. The per-finger normal grip-force target, alpha_m (default 1.0 N, thumb = 2×), is the knob to sweep. Weight is \(mg = 0.2\,\text{kg}\times 9.81\,\text{m/s}^2 \approx 1.96\,\text{N}\); with the physical cube's \(\mu_\text{static}=0.8\) (from the SDF), a 3-finger symmetric squeeze needs roughly \(\sum_i \mu \lambda_n^i \ge mg\), i.e. an analytical static threshold around \(\alpha_M \approx 0.6\,\text{N}\) per finger before margin — the file's default of 1.0 N is already a ~1.6× safety margin over that estimate. Objective: confirm the hold empirically and find where it actually breaks as the grip target is swept down.

As of the current defaults, --alpha_m is inert unless you also raise --w_lambda. alpha_m only enters the problem through C3's force-reference cost (§4.3), which is gated by --w_lambda — now 0.0 by default (see §5). With the force-reference cost off, the live grip-force knob is --force_floor (§4.5/§4.6), which is not multiplied by alpha_m and must be set independently. To actually sweep the friction threshold in the sense of §1a, sweep --force_floor (and, if you want C3's own plan to also target it, pass --w_lambda>0 together with --alpha_m).

1b. The control-architecture — who actually produces the force?

C3 never sends torque to the plant directly. It is a planner (solved roughly once per LCS timestep, ~40 ms) that outputs a planned state trajectory and a planned contact-force trajectory \(\lambda\); a single, fixed executor — a task-space PD + Jacobian-transpose grip law, running every 1 kHz control tick (§4.5–4.6) — turns C3's projected force output into joint torque. This mirrors the real push-anything Franka pipeline's split between a slow C3 planner and a fast executor — see franka_sampling_c3_controller.cc / franka_osc_controller.cc for the production analogue, which instead uses a full inverse-dynamics QP ("OSC") as its executor. Earlier revisions of this file carried that OSC QP plus two other realization strategies as an explicit A/B/C/D comparison; that comparison is now settled and only the task-space PD+Jᵀ law remains (see §5 for what was given up by dropping the QP — mainly, no explicit friction-cone or torque-box enforcement inside the executor itself). The objective for this file going forward is narrower: characterize how much of the resulting hold is attributable to C3's plan versus the executor's own impedance regulation (the --plan_debug Factor-1/2a/2b diagnostics in §4.4 are for exactly this).

A tertiary, optional test is baked in via --cube_bob_amp: once the grip is confirmed to hold a static reference, replacing the cube's z-target with a sine gives C3 a genuine nonzero tracking error to chase, distinguishing "can hold" from "can move."

2b. The robot

A right Allegro hand (drake_models URDF), welded to the world at (0, 0, 0.5 m) with the palm rotated to face up (RollPitchYaw(π/2, −π/2, 0), see allegro_hand_utils.cc). 16 actuated DOF across four 4-joint fingers; only three are used for grasping:

The two-vs-one layout (index+middle on −Y, thumb on +Y) is the grasp geometry analyzed in grasp_theory_critique 2.html's force/moment balance. The thumb is seeded to a bent pre-shape (SetThumbSeed: joints 12–15 = 1.0, 0.5, 0.5, 0.3 rad) before every IK solve so the solver doesn't converge to a straight-thumb local minimum.

2c. The object

urdf/numbered_cube/numbered_cube.sdf: a 6 cm cube, mass 0.2 kg, diagonal inertia \(1.2\times10^{-4}\,\text{kg·m}^2\) per axis, single box collision geometry with Drake proximity friction μ_static = 0.8, μ_dynamic = 0.5. Six textured faces (for visual identification only — collision is one box, so "which face" is determined entirely by finger placement, not by the collision geometry; see grasp_questions_answered.html Q1). Starts upright at world position X_WC0 = (0, 0, 0.58), which stays the fixed pose reference for the whole run.

The LCS's own friction assumption is a separate flag, --mu (default 0.5), used only to build the LCS's complementarity constraints — it matches the cube's μ_dynamic but is more conservative than its μ_static = 0.8. Nothing downstream of the LCS enforces a friction cone. The executor (§4.6) is a plain PD + Jᵀ law: it commands whatever normal force C3 (or --force_floor) asks for, with no check that the resulting fingertip force actually lies inside any friction cone. Slip prevention today rests entirely on (a) the LCS's own belief about \(\mu=0.5\) being realistic and (b) the physical cube's real \(\mu_\text{static}=0.8\) being at least that generous. There is no code-level guardrail if either assumption is wrong.

2d. Collision filtering (making the physics world match the model world)

  • Thumb-vs-palm exclusion (always on): the thumb's five links are filtered against the palm to prevent a SAP impulse blow-up at the knuckle.
  • Cube isolation (--isolate_cube, default true): every hand geometry except the three grasping fingertips is filtered against the cube. This is the lever that makes the real physics world match the LCS's model world by construction (the LCS only ever knows about three contact pairs — anything else touching the cube would be an unmodelled force). The file's own comment flags the caveat: the reach phase relies on full-hand collision to help seat the fingers, so this could in principle stop index/middle from ever making contact; it's gated behind the flag for A/B testing.

2e. Visualization & interactive setup

Meshcat at 60 Hz publish rate, plus a ContactVisualizer for force glyphs. Small red spheres mark the three live grasp targets, and a coordinate triad marks the cube frame. Camera fixed at (0.7, 0.7, 0.8) looking near (0, 0, 0.55). Before the control loop starts, the binary poses the hand at q_pregrasp and then q_contact and pauses on each for a keypress ("STATIC PREVIEW... Press Enter to continue") — a manual visual sanity check of the IK solutions before any simulated time is spent.

2f. How control actually attaches to the plant

There is no wired Drake controller System in this diagram. The hand's actuation input port is a single FixValue handle (act_fixed), and the control loop is a bare for over t in 1 ms steps that (1) reads sensor state from plant_ctx, (2) computes tau_hand in plain C++, (3) writes it into act_fixed, and (4) calls simulator.AdvanceTo(t). All control logic — phase machine, C3, the grip law — lives imperatively outside the systems-framework diagram, not as a LeafSystem.

The cube "pin" during the reach phase and the first 0.5 s of kC3 is likewise not a Drake joint or constraint — it is a kinematic teleport: every tick, while cube_pinned, the loop force-overwrites the cube's position/velocity back to q_cube0 / zero, after AdvanceTo has run. So the physics briefly moves the cube each tick and the loop immediately erases that motion.

3. High-Level Understanding

The file implements a two-phase grasp controller, and the split exists because contact-implicit trajectory optimization is bad at exactly the sub-problem that "reaching" is (a large, mostly-empty-space search with combinatorial contact possibilities) and good at exactly the sub-problem that "holding" is (a small, local correction near a known, already-established contact configuration).

PhaseSub-problemMethodWhy this method
kReachMove the 3 fingertips from open pose to touching the cube faces. Scripted cubic spline + PD, cube kinematically pinned. Deterministic, well-conditioned, no need for an optimizer to "discover" contact — the touching is guaranteed by construction and confirmed by the real physics before C3 ever starts (see grasp_questions_answered.html Q3).
kC3Maintain grip against gravity once contact is real and the cube is released.C3/ADMM plans (a short-horizon MPC over a locally linearized contact model), a task-space PD + Jacobian-transpose grip law executes.The linearization is only valid near the current contact state — exactly the regime this phase operates in.

3a. The original hypothesis

The design intent (stated in the file's own header comment) was that the squeeze force should not be hand-commanded at all — it should emerge: anchor the cube's pose in C3's cost with a large weight (w_cube), and since gravity will pull an unsqueezed cube away from that anchor, C3's optimizer is forced to find enough friction force, \(\sum_i \mu\lambda_n^i \ge mg\), to keep the cost low. "The squeeze force is not commanded — it emerges from 'cube must not fall.'"

3b. What was actually found

That hypothesis is only half true, and the file (together with grasp_questions_answered.html Part 2) documents why in detail. In C3's ADMM formulation, the contact force \(\lambda\) is a free decision variable in the cost-minimizing QP sub-problem. So when C3 is asked "how do you keep the cube up?", the cheapest answer is to imagine a \(\lambda\) that holds it, without ever committing the input torque \(u\) that would be needed to physically produce that force. Applying C3's raw solved torque directly — a realization strategy this file no longer includes, see §4.5's note — was documented to collapse from tens of Nm to ~0.2 Nm the instant the cube is released — a structural failure, not a tuning one (verified against ADMM iteration count, horizon length, and cube-cost weight, per the code comments).

3c. The fix that's actually in the file today

The working configuration splits the job the same way the production push-anything pipeline does: C3 is a planner (solved roughly once per LCS timestep, ~40 ms), and a separate, higher-rate (1 kHz) executor — a task-space PD + Jacobian-transpose grip law, no QP — turns C3's planned fingertip positions and contact-force targets into joint torque, plus C3's raw input as feedforward. Practically, most of the "hold" observed in testing comes from the executor's own impedance regulation toward a fixed geometric grasp-point reference (not from tracking C3's own predicted trajectory — that path, --fk_target=true, is documented to let the cube sag, because C3's plan is itself still largely passive). C3's live contribution is the grip-force magnitude target it feeds the executor's force term. Making C3's own plan carry real corrective effort (so that tracking the plan, not a fixed geometric reference, is what holds the cube) is called out in the docs as the open problem.

An earlier revision of this file also carried a full inverse-dynamics QP ("OSC") executor — with an explicit friction cone and torque-box constraint inside the QP — plus two other realization strategies, selectable via flags, as an explicit comparison. That comparison concluded the QP wasn't necessary for the hold to work, and the file was simplified down to the single PD+Jᵀ law described here. The trade-off from dropping the QP (no friction-cone / torque-box enforcement inside the executor) is discussed in §5.

4. Low-Level Walkthrough

4.1 The control loop & phase machine

for (t = control_dt; t < sim_time; t += control_dt), control_dt = 0.001 s, sim_time default infinite (runs until killed). Each tick:

  1. Read hand velocities and the SAP contact-results port; for each of the 3 tip↔cube pairs, mark touching[i] if the reported contact force norm exceeds --contact_force_thresh (0.02 N).
  2. Branch on phase (kReach / kC3) to compute tau_hand.
  3. In kC3, clamp tau_hand to ±tau_max (100 Nm); the reach phase is left unclamped since it needs 30–80 Nm transient peaks to track the spline against the initial SAP settling.
  4. Write torque, simulator.AdvanceTo(t).
  5. If still pinned, re-teleport the cube back to its reference pose/zero velocity.
  6. Update Meshcat markers; every 0.25 s wall-simulation-time, print throttled diagnostics (§4.8).

4.2 Phase 1 — kReach

IK. Two target configurations are solved once, up front, on the sim plant's own context (SolveGraspIK, ±1 mm position-constraint tolerance per fingertip frame, seeded from the thumb pre-shape):

  • q_contact: fingertips at cube_size − 0.01 = 0.05 m half-extent offset from the cube center — i.e. 5 mm inside the nominal face. Deliberate interpenetration, so the contact gap \(\phi \le 0\) at handoff (complementarity needs a closed gap before it will allow any normal force at all — see grasp_theory_critique.html Q3).
  • q_pregrasp: fingertips cube_size + 0.02 = 0.08 m — 2 cm outside the face, seeded from q_contact so the solver approaches from the same direction rather than a wrapped-around local minimum.

Both use GetGraspPositions(X_WC0, size, a=−0.02, b=0.02, c_off=0.0): index and middle land on face 4 (−Y) at local-x offsets −2 cm / +2 cm; the thumb lands on face 3 (+Y) centered (c_off = 0).

Trajectory. A shape-preserving cubic spline (PiecewisePolynomial::CubicShapePreserving) in the full 16-DOF hand joint space from q_pregrasp to q_contact over --t_contact (5 s default); its derivative gives the velocity feedforward.

Control law. \(\tau = k_p(q_\text{tgt}-q) + k_d(\dot q_\text{tgt}-\dot q) + \tau_g\), with --kp (200 Nm/rad default — raised from an earlier 10, which was documented as too soft to seat the fingers against gravity: only the thumb ever made contact and the handoff to C3 never fired) and --kd (1.5). Once a finger's touching[i] latches (guarded by --contact_enable_t, 1.0 s, so an accidental near-cube start pose can't false-trigger), that finger's target is overridden to hold at q_contact for the rest of the phase (a real inward preload, not just a graze), while the other fingers keep following the spline.

Handoff condition: all three arrived[i] simultaneously true.

4.3 Handoff — building the LCS and the C3 problem

The instant all three fingers are in contact, the following happens once:

  1. Read the full 45-dim state from sim_plant, sync it into lcs_plant's context.
  2. LCSFactory::LinearizePlantToLCS builds the LCS \(x_{k+1}=Ax_k+Bu_k+C\lambda_k+D\), \(0\le\eta_k\perp\lambda_k\ge0\) at this state with \(u=0\), over the 3 tip↔cube contact pairs, using lcs_opts (contact model, N=5, dt=0.04 s, 3 contacts, 2 friction directions, mu=0.5).
  3. Print the raw contact gaps \(\phi\) (should read \(\le 0\)) as a sanity check, plus \(\lVert A\rVert, \lVert B\rVert, \lVert D\rVert\).
  4. Input scaling. \(s_u = \lVert A\rVert/\lVert B\rVert\) (or --input_scale to override), applied by rescaling \(B\); \(R\) is compensated by \(s_u^2\) so this is a pure change of variables on \(u\), not a physical change — it exists purely to condition the QP and avoid an OSQP DualInfeasible report.
  5. Desired state \(x^*\): the three grasping fingers at q_contact, the ring finger held at its current position, the cube at q_cube0, all velocities zero. Repeated across all \(N{+}1\) knots.
  6. Cost matrices (fixed for the whole run unless the moving-reference logic overrides the target, §4.4):
    • \(Q\): block-diagonal — k_hold=10 on the 16 hand-joint positions (keeps fingertips seated), w_cube=1000 on the cube's 7 pose DOF (the load-bearing anchor term), w_vel=0.1 on the 16 hand-joint velocities, and w_cube again on the cube's 6 velocity DOF.
    • \(R = s_u^2\cdot\)w_R\(\cdot I\), w_R=0.01, on the 16 inputs.
    • \(G,U\): ADMM augmented-Lagrangian weights, w_G=w_U=1.0, both \(n_z\times n_z\).
  7. C3Options: admm_iter=3 (deliberately few — the code comment flags this as a likely under-convergence culprit if λ looks right but torque doesn't follow), rho_scale=3, warm_start=false, scale_lcs=true, gamma=1.0.
  8. Construct c3 = C3Plus(lcs_init, CostMatrices(Q,R,G,U), x_desired, c3_opts) — the C3+ variant, which carries an extra explicit consensus variable \(\eta\), so \(n_z = n_x+n_u+2n_\lambda\) rather than plain C3's \(n_x+n_u+n_\lambda\).
  9. Force-reference cost (if --w_lambda > 0 — default 0, i.e. off — this is the fork's local addition to the C3 core, see the "c3 is forked locally" project note): a per-contact cost \(w_\lambda\lVert\sum_{j\in g_i}\lambda_j-\alpha_i\rVert^2\), target \(\alpha_i=\) alpha_m for index/middle, \(2\cdot\)alpha_m for thumb (force closure, per the a/b/c geometry ratio in grasp_theory_critique 2.html). For Stewart-Trinkle each group \(g_i\) is the single λ_n entry at index \(3+i\); for Anitescu it's the whole per-contact cone block (normal force = sum of the cone edges), built as a rank-1 \(w_\lambda\mathbf{1}\mathbf{1}^\top\) block instead of a diagonal one so the group's sum hits the target.
  10. Input box constraint: \(|\tilde u_i|\le\)tau_max\(/s_u\) per joint, added as a QP constraint — bounds the feasible set and removes an unbounded-primal failure mode at pin release.
  11. OSQP options set on c3: max_iter=4000, eps_abs=eps_rel= --osqp_eps (1e-3), warm-starting/polishing/adaptive-rho on, rho=1e-4, sigma=1e-6, alpha=1.6, scaling=15, check_termination=25.

phase flips to kC3; handoff_t is recorded (the cube stays kinematically pinned for a further 0.5 s "warm-up" before physical release).

4.4 Phase 2 — kC3

Decimation

C3 is expensive relative to the 1 kHz control tick, so re-linearization and solving are decimated independently: do_relin fires every --relin_period_steps ticks (40, i.e. once per c3_dt), do_solve every --c3_period_steps ticks (also 40 by default). Between fires, the previous C3 solution is simply reused. Both are profiled (relin_ms_sum/max, solve_ms_sum/max — accumulated but, as written, never printed; see §5).

Re-linearization (if due)

Rebuilds the LCS at the current state, rescales \(B\) by the same \(s_u\), caches the fresh contact gaps for the diagnostic prints, and calls c3->UpdateLCS.

Moving reference (if --cube_bob_amp ≠ 0 and the cube is released)

Overwrites the cube-z position and velocity target across the entire horizon (all \(N{+}1\) knots, phase-correct per knot) with a sine of period --cube_bob_period (3 s) around \(z_0=0.58\). Zero amplitude (default) leaves the static target from handoff untouched.

Solve (if due)

c3->Solve(x_current). Every solve prints one summary line plus, if --plan_debug (default true), three diagnostic factors used to localize failure:

FactorQuestionHow it's computed
F1Does the plan itself believe it holds, and how expensive is that? Planned cube-z at each knot (GetStateSolution) plus per-knot state cost \(J_k=(x_k-x_k^*)^\top Q(x_k-x_k^*)\) and its sum \(J_\text{tot}\).
F2aIs the committed plan physically feasible? ADMM consensus residual \(\lVert z_k-\delta_k\rVert\) per knot — \(z=\)GetFullSolution (cost/dynamics-optimal, may violate complementarity), \(\delta=\)GetDualDeltaSolution (complementarity-projected, physically feasible). Large gap ⇒ no single trajectory is both wanted and feasible.
F2bDid the executor achieve what last solve predicted one step ahead? x_current − x_plan_prev (cube position/quaternion, hand-joint norm), where x_plan_prev is last solve's GetStateSolution()[1] — meaningful because solves are spaced one c3_dt apart.

4.5 Torque realization — two branches

Selected each tick by the cube-pin state (no flag selects between realization strategies anymore — there is only one, once released):

  1. Warm-up (cube_pinned == true). Same PD-hold-at-q_contact law as the reach phase. C3 is already solving in the background, but its output is not applied yet — this exists because C3's cost gradient on a still-pinned cube is near zero, so without this the fingers would drift off the cube during warm-up.
  2. Released — the task-space PD + Jacobian-transpose grip law (§4.6). Builds a per-finger desired normal force \(f_{n,i}=\max(0,\ \lambda_{n,i}^\text{proj},\ \)force_floor\()\) (thumb floor doubled) from C3's projected λ (GetDualDeltaSolution, clamped ≥0 — not the raw QP copy, which can be negative), and a position target either fixed to the reference-cube grasp points (default) or the forward-kinematics of C3's planned next hand config (--fk_target=true), then applies §4.6's control law plus C3's raw \(u\) as feedforward.
Earlier revisions of this file selected among four realization strategies here (this one, a PD-track-the-plan-plus-Jᵀλ layer, a full inverse-dynamics QP "OSC" executor, and applying C3's raw torque directly). All but this one have been removed; see §3c and §5.

4.6 The grip law — task-space PD + Jacobian-transpose, no QP

Applied directly, every 1 kHz control tick — no optimization problem is solved for this step (unlike the removed OSC executor, which posed a QP with an explicit friction-cone and torque-box constraint; see §5 for what that trade-off costs):

\[ \tau \;=\; \tau_g \;+\; \sum_{i=1}^3 J_i^\top\big[\,K_p(p_i^\text{des}-p_i) - K_d\,\dot p_i + f_{n,i}\,\hat n_i\,\big] \;+\; s_u\cdot u_0^\text{C3} \]
Term / symbolMeaning in code
\(\tau_g\)Gravity-compensation torque for the 16-DOF hand (CalcGravityGeneralizedForces).
\(J_i\)Fingertip translational Jacobian, hand columns only (CalcJacobianTranslationalVelocity, left-cols to the 16 hand velocities).
\(K_p, K_d\)--task_kp (100), --task_kd (20) — task-space PD gains on fingertip position/velocity error.
\(p_i^\text{des}\)Fixed grasp point on the reference cube, or C3's planned-config FK if --fk_target (§4.5).
\(\hat n_i\)Inward press direction: current cube rotation \(R_{WC}\) times a fixed cube-frame vector — \((0,1,0)\) for index/middle (press toward +Y, into the −Y face), \((0,-1,0)\) for thumb.
\(f_{n,i}\)\(\max(0,\lambda_{n,i}^\text{proj},\)force_floor\()\) — see §4.5. Not clamped to any friction cone — whatever this evaluates to is commanded as-is.
\(s_u\cdot u_0^\text{C3}\)C3's raw scaled input solution, added as feedforward.

The only constraint applied to this law's output is the global \(\pm\)tau_max clamp at the loop level (§4.1) — there is no per-contact friction-cone check and no QP-level torque-box constraint inside the law itself.

5. Gaps, Gotchas & Things Worth Knowing

The documented "working" hold is not the default configuration. --force_floor defaults to 0.0. Its own docstring says 0 means "realize C3's force as-is (which collapses to 0 at release)." The stable hold described in grasp_questions_answered.html Part 2 ("First stable hold of the whole session") was obtained with the grip floor on. Running the binary with all defaults therefore reproduces the documented near-zero-grip failure mode at the executor, not the documented success — you need --force_floor≈alpha_m (e.g. 1.0) explicitly on the command line to get the behavior the docs describe as working.
--w_lambda now defaults to 0 — C3's own plan no longer targets alpha_m at all unless you turn it back on. With the force-reference cost off, C3's planned λ is shaped only by the cube-pose anchor (w_cube) and whatever the LCS's dynamics imply, not by any explicit per-finger force target. --alpha_m is inert by default (see §1a). The grip actually commanded to the plant is governed almost entirely by --force_floor, which is a separate number you set directly — it is not derived from alpha_m in any way at the moment.
Gap inflation (--phi_offset) has been removed entirely — the φ≈0 hover-band flicker it existed to fix is back in play. grasp_questions_answered.html Part 2 documents that the physical contact gap hovers at \(\phi\approx0\pm1\,\text{mm}\) (SAP equilibrium noise), and strict complementarity gates the LCS's λ to zero the instant \(\phi\) reads positive — an "absorbing zero-grip equilibrium." Gap inflation was the standard contact-implicit relaxation added specifically to keep the contact representable across that noise band. With it gone, if the grip intermittently drops right around the release moment (or during re-linearization while released), this mechanism is the first thing to suspect — the fix, if needed, is either to reintroduce a form of gap relaxation or to lean more on --force_floor to paper over the gap (the floor is applied downstream of the LCS, so it isn't affected by this complementarity gating).
The executor enforces no friction cone and no torque box of its own. The removed OSC layer solved a QP subject to \(\hat n^\top f\ge0\), \(|\hat t^\top f|\le\frac{\mu}{\sqrt2}\hat n^\top f\), and \(|\tau|\le\tau_\max\). The task-space PD+Jᵀ law that replaced it (§4.6) has none of that — it computes a torque directly from the position/force error terms and only gets clamped to \(\pm\)tau_max at the outer loop level (§4.1), with no per-contact check that the commanded force is physically realizable through friction. --mu is now used only by the LCS; it has no effect on what the executor actually commands.
Profiling counters are collected but never printed. relin_ms_sum/max, solve_ms_sum/max, relin_calls, solve_calls are accumulated every cycle (§4.4) but there is no print statement anywhere in the loop or after it (and since sim_time defaults to infinity, "after the loop" never happens in practice). The ~11 ms solve-time figure in the project notes came from ad hoc instrumentation, not from anything this binary currently surfaces on its own.
The ring finger is present but entirely unmanaged. It is part of the 16-DOF actuation vector and gets whatever the reach-phase spline computes for it (it's included in q_pregrasp/ q_contact from the IK, since IK only constrains the other three tips, so its resting pose is whatever the solver happens to leave it at) — it is never targeted, never checked for arrival, and is excluded from --isolate_cube's protected set only in the sense that it's one of the "non-tip" geometries filtered away from the cube. Cosmetic in this experiment, but worth knowing if a future version wants a 4-finger grasp.
C3's raw output is logged but never applied directly. The grip law uses the projected λ (GetDualDeltaSolution) rather than the raw QP λ (GetForceSolution), because the raw copy is not projected onto \(\lambda\ge0\) and can go negative. The per-solve diagnostic print, however, prints the raw GetForceSolution() value — so the number printed to the console each solve ("C3 λ_n=...") is not the number actually driving the grip law's force target. Easy to misread while eyeballing logs.
admm_iter=3 is explicitly flagged as suspicious in the code, not just low. The flag's own docstring: "if C3 reports a grip force (λ_n≈target) but commands ~0 torque and the cube drops at pin release, it likely has not reconciled (u, λ). Try 10–30." This is precisely Factor 2a in the plan-quality diagnostics (§4.4) — worth checking that residual before assuming any failure is a modeling problem rather than an under-converged ADMM solve.
Everything downstream of C3 depends on c3 being non-null. The kC3 branch dereferences c3 unconditionally (it's constructed once, at handoff, and never reset) — there's no path back to kReach and no recovery if the LCS build or the solve fails. Nowhere in the file is a solver's result.is_success() checked at all — a failed C3 solve would silently reuse stale solution accessors rather than erroring visibly.
